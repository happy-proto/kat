# Parser 表的体积与构建性能

## 方案与依据

发布构建把 Tree-sitter 大状态表转换为原生紧凑表，保留前两个状态直接索引，再以 Zstd level 19 分语言压缩。每种语言首次使用时按需解压，并发初始化只执行一次；解压后的表保留到进程结束。普通本地构建不启用压缩，`just compact-release` 使用发布路径。

统一处理全部 parser，避免按语言维护特殊编码或大小阈值。原生紧凑表复用 Tree-sitter 的查找方式，无需自定义运行时解码结构。Zstd level 19 在既有 127 个表的参数比较中比 level 3 少约 1.10 MiB，level 20～22 对最大 parser 只再节省约 0～2.7 KiB；共享字典计入自身后没有净收益，因此不引入字典和训练流程。

体积优化需要权衡解析速度与首次使用时的堆内存，不能只比较压缩文件大小。最大的 SystemVerilog 表在紧凑布局下解压约 5.53 MB，密集布局约 21.7 MB；紧凑查找可能增加纯解析时间。当前目标是最大语言的大文件端到端耗时增量约 20 ms 以内，仍需在不同平台和输入上观察。

## 表导出与压缩阶段

在 Apple M1 Pro / macOS ARM64 上，对 135 个 parser 分别执行 1 路和 4 路导出与 Zstd level 19 压缩，单次测量如下：

| 并行数 | 阶段耗时 |
| --- | ---: |
| 1 | 72.16 秒 |
| 4 | 23.57 秒 |

两次使用相同源码、头文件、编译器和压缩参数，所有改写后的 `parser.c` 逐字节一致；输入复制与 Cargo metadata 查询不计入计时。约 3.06 倍的加速只对应表导出与压缩阶段，不代表完整发布构建或运行时解析速度。

任务独占临时编译目录、压缩器和目标文件；同一 crate 的 checksum 清单串行更新。默认并行数有上限以控制内存，`--jobs 1` 可顺序复核。实际发布构建耗时以 CI 的 Cargo/linker timing 为准。

## 二进制与运行时基线

以下测量来自较早的 131-parser 源码快照，用于说明方案取舍，不是当前提交的体积或速度保证。在同一快照、macOS ARM64、静态链接 dav1d 的 release 构建中：

| 构建 | 安装后的二进制大小 |
| --- | ---: |
| 未压缩 | 159,520,064 字节（152.13 MiB） |
| 紧凑表 + Zstd | 37,120,384 字节（35.40 MiB） |

体积减少约 76.7%，两版均未动态链接 dav1d 或 Zstd。103 个 showcase 文件及 427 KiB SystemVerilog 样本的 `--debug-analysis` 输出逐字节一致。

低负载下，两版 `kat` 命令交错运行各 16 次，完整输出写入 `/dev/null`：未压缩中位数 450.09 ms，压缩中位数 465.26 ms，逐对差值中位数 +15.11 ms。该结果仅覆盖该机器和样本，不能推广为所有语言的性能结论。

## 持续验证

CI 在支持的平台上验证压缩 parser 的发布构建、可执行文件冒烟测试和静态依赖。运行时比较应同时记录首次初始化与稳定解析，并使用相同源码、输入、机器和输出方式；输入规模、机器负载和冷暖缓存都可能影响结果。
