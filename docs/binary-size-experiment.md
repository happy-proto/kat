# 发布二进制体积实验

## 目标与已选方案

- 目标是减小安装后的未压缩 release binary，保留全部语言与功能；性能比较以真实 `kat` 命令的端到端耗时为准，最大语言的大文件场景允许约 20 ms 以内的额外耗时。当前不优先引入 LTO，也不考虑只压缩大于某个阈值的 parser；统一方案需覆盖全部实际链接的 parser。
- 已实现 Tree-sitter 原生紧凑表 + Zstd，所有 parser 一视同仁，按语言延迟解压。编译期使用 Zstd level 19，不引入训练字典。CI 的静态发布构建及本地 `just compact-release` 使用相同流程。

## 全部 parser 的实际构建

- 在同一提交、macOS arm64、静态链接 dav1d 的 release 构建中，未压缩的完整 `kat` 为 159,520,064 字节（152.13 MiB）；压缩 131 个依赖 parser 后，完整 `kat` 为 37,120,384 字节（35.40 MiB），减少 116.73 MiB，约 76.7%。两版都未动态链接 dav1d 或 Zstd；这里比较的是安装后 binary 本身的大小，而非归档或 gzip 体积。
- 压缩构建的 262 个测试全部通过；103 个 showcase 文件和 427 KiB SystemVerilog 样本的 `--debug-analysis` 输出与未压缩构建逐字节一致。低负载下两版 `kat` 命令交错运行各 16 次，完整输出写入 `/dev/null`，未压缩中位数 450.09 ms、压缩中位数 465.26 ms，逐对差值中位数 +15.11 ms，处于约 20 ms 的目标内。

## 完整二进制对比

- 设计阶段在另一份源码快照上，macOS arm64 静态链接 dav1d 的基线为 152.13 MiB。实际链接的 127 个 parser 的大状态密集表合计 96.16 MiB。逐个提取全部 parser 的表，并以只改造最大 SystemVerilog parser 的完整静态构建校准，得到以下安装后完整二进制估算；表中的 Zstd 候选按 level 3 比较，除基线外均不是全 parser 实际链接产物。正式构建实测见上节：

  | 统一处理全部 parser 的方案 | 完整二进制估算 | 最大 parser 的 427 KiB 输入端到端差异 |
  | --- | ---: | ---: |
  | 当前基线 | 152.13 MiB（实测） | 基准约 454 ms |
  | Tree-sitter 原生紧凑表，首两个状态仍用直接索引 | 90.86 MiB | +13 ms |
  | 原生紧凑表 + LZ4 / Zstd / Snappy 按语言延迟解压 | 40.23 / 37.19 / 42.32 MiB | +14 / +18 / +16 ms |
  | 原始密集表 + LZ4 / Zstd / Snappy 按语言延迟解压 | 62.63 / 58.32 / 66.24 MiB | +6 / +6 / +4 ms |
  | 自定义位图 + LZ4 / Zstd / Snappy 按语言延迟解压 | 59.08 / 57.69 / 59.95 MiB | +6 / +11 / +7 ms |

## Zstd 参数实验

- 对已选方案再比较 Zstd level 1 / 3 / 6 / 9 / 12 / 15 / 19：127 个表压缩数据合计分别为约 6.15 / 5.01 / 4.62 / 4.59 / 4.57 / 4.54 / 3.86 MB。level 19 相对 level 3 少约 1.10 MiB，校准后的整包估算约 36.08 MiB。只替换 SystemVerilog 的真实静态构建从 137,126,432 字节降到 137,059,440 字节，427 KiB 样本端到端配对中位数相对基线约 +19 ms，level 3 与 level 19 几乎相同。level 20～22 对该最大 parser 只再节省约 0～2.7 KiB，不优先使用。
- 对全部 127 个表训练一份共享 Zstd 字典时，16 / 64 / 110 KiB 字典计入自身后，总数据分别比无字典增加约 13 / 48 / 88 KiB。单独对 SystemVerilog 的表切块训练字典也未得到净收益。因此不把字典或训练流程加入正式构建。Zstd 字典通常帮助许多相关的小文件；这里每种语言只有一张独立表，已有连续数据足以让普通压缩建立匹配。

## 编码与性能依据

- 原生紧凑表模型依照 Tree-sitter 小状态表结构，统计全部 127 个 parser 的密集行转换后的分组、符号、映射表和已有小状态表数据，并以真实重新生成的 SystemVerilog parser 校准。其模型编码与真实 SystemVerilog 生成结果的压缩大小相差约 0.3%～3.4%；模型对全 parser 链接的预测已由正式构建实测替代。该方案需要修改 grammar 生成过程中的状态划分，不是 Tree-sitter 当前提供的构建开关。相同编码器下，自定义位图比直接压原始密集表的数据再少约 3.55 MiB（LZ4）、0.62 MiB（Zstd）或 6.28 MiB（Snappy），但需要额外的自定义编码和还原代码。
- 最大的 SystemVerilog 密集表约 21.7 MB。首次按需解压的微基准中，直接 LZ4 / Zstd / Snappy 约需 1.5 / 4.6 / 2.0 ms，位图 + LZ4 / Zstd / Snappy 约需 2.2 / 3.4 / 2.4 ms。直接解压和位图还原后都恢复同一张密集表，稳定解析 427 KiB 样本各三次时分别约 159.1 / 159.3 ms，当前原表约 158.5 ms。表中的端到端数据来自同一轮交错运行的 SystemVerilog 静态构建，只有该 parser 使用新方案；样本、机器负载和冷暖缓存都会影响数值，接近 20 ms 上限时仍需复测。首次使用时需在堆上还原表；位图实现还多用一块临时缓冲区。
- SystemVerilog 原生紧凑表把原有大状态行也转为紧凑结构，仅保留前两个状态直接索引，427 KiB 样本重复解析三次的纯解析耗时由约 167 ms 升至约 282 ms；压缩后仍使用同一紧凑查找方式。真实 `kat` 命令的大样本端到端差异见表；已选 level 19 在当前机器上接近 20 ms 上限，其他平台和更大输入仍需复核。小样本在此次测量中更快，尚未确认具体原因。原生紧凑表压缩后，SystemVerilog 首次使用时需在堆上还原约 5.53 MB 数据，而密集表压缩后需还原约 21.7 MB。当前 grammar 主要来自预生成 parser crate；这些方案都要在 parser 生成或编译阶段改写表。压缩方案还要维护跨平台静态 Zstd 库与延迟初始化，单改 `kat` 的运行时无法实现。应优先设计可复用的 parser 构建/打包层，避免为每个 crate 手工维护补丁。

## 后续验证

- CI 的发布构建矩阵在 Linux、macOS、Windows 上复核构建和静态依赖；后续持续观察不同输入规模的端到端耗时。最大样本的逐字节输出对照目前只覆盖 SystemVerilog。
